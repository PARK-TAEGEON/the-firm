### 초기 저자 설정 조정과 기한 준수 경로

초기 제안의 `jung-review` 및 정민호 사건 기한은 day 2였다. 단일 담당자의 하루 최대 4시간으로 자료 정리 8시간 후 기록 검토 12시간을 진행하면, 어떤 배정으로도 그 기한을 지킬 수 없었다. 풀 수 없는 상황을 최적화 과제로 제시하지 않도록 **두 기한을 day 3으로 조정**했다. 이는 이 실험의 authored 시나리오 수정이며 실제 법원 기일 변경 또는 Accepted DEC 변경이 아니다. 자료 정리 자체의 day 1 기한은 유지한다.

수임 수락을 포함해 모든 업무 기한을 지킬 수 있는 재현 경로는 다음과 같다. 우선순위는 기본값 그대로다.

1. 윤지훈 사건을 수임한다. 정민호 자료 정리는 김현우, 고은아 조사 메모는 이정우, 윤지훈 자료 취합은 박서윤, 윤지훈 준비 보고는 김현우에게 배정한다. 다른 업무는 기본 담당자를 유지한다.
2. day 0을 진행한다. 정민호 자료 정리를 박서윤에게 인계한다. 이미 수행한 4시간은 유지된다.
3. day 1을 진행한다. 고은아 조사 메모를 박서윤에게 인계한다. 이미 수행한 6시간은 유지된다.
4. 나머지 day 2·3·4를 진행한다.

완료일은 정민호 자료 정리 1 / 기록 검토 3, 고은아 조사 메모 2 / 검토 마무리 3, 윤지훈 자료 취합 0 / 초기 검토 4 / 준비 보고 4다. 이는 유일한 정답이나 추천 최적해라는 뜻이 아니라 **선택으로 기한 준수가 가능하다는 검증 사례**다. 마지막 날 생성된 윤지훈 잔금 120만원은 day 5 지급 예정 미수금으로 남는다. 추가 인계 비용은 이 실험에서 생략된다는 아래 경계를 함께 적용한다.

## 3. 스케줄링·기한·보고

1. 매일 사람별 공유 잔여 capacity를 만든다. 사건별로 새 capacity를 만들지 않는다.
2. 미완료·배정됨·직무 적격·선행 조건 완료인 업무만 실행 후보가 된다.
3. 후보는 우선순위 1(높음) → 2(보통) → 3(낮음), 동률은 고정 task ID 오름차순이다. 기한은 자동으로 우선순위를 바꾸지 않는다.
4. 후보 하나에 `min(남은 업무량, 담당자 잔여 capacity)`를 투입한다. 부분 수행은 보존한다.
5. 같은 날 선행 작업이 완료되면 후속 업무를 다시 후보에 넣는다. 담당자의 잔여 capacity가 있을 때만 수행한다. 날짜 안의 실제 시각·이동시간은 모델링하지 않는다.
6. 실제 누적 수행량이 요구량에 도달해야 `completedDay`와 완료 기록이 생긴다. 보고 문구는 시나리오에 작성된 자료 검토 결과이며 범용 법률 추론 결과가 아니다.
7. 기한 당일 업무 처리 후 미완료면 그날 보고의 `lateTasks`에 포함한다. 이후에도 미완료인 동안 남는다. 자동 벌금·승패·징계·고객 이탈은 만들지 않는다.
8. 담당 변경은 이미 수행한 작업량·과거 담당자별 시간·비용·보고를 지우지 않는다. 이 짧은 동일 사무실 시나리오에서는 기존에 공유된 자료 범위를 인계하며 별도 인계 시간은 계산하지 않는다.

`cases.status='ready'`는 포함된 **준비 업무가 끝났다**는 뜻이다. 법정 준비의 충분성, 의뢰 목표 달성, 사건 종결·승소를 뜻하지 않는다. 미완료 task의 `outputText`는 작성된 콘텐츠 정의이며 UI는 `completedDay!==null`인 경우에만 실제 완료 결과로 보여야 한다.

## 5. 예측과 확정 사실

`forecast`는 상태를 복사하여 **실제 일일 스케줄링 함수와 같은 함수**로 day 4까지 투영한다. 원본 상태·지속 보고 기록을 변경하지 않는다.

- 수임 미결정일 때는 이미 확정된 기존 업무만 계산하고 `requiresIntakeDecision=true`를 반환한다.
- 현재 배정·우선순위·정해진 작업량·가용시간·예정 입금이 유지된다는 조건이다. 새로운 사건, 결근, 추가 요청, 입금 지연, 법률적 불확실성은 계산하지 않는다.
- `days`는 아직 처리하지 않은 날짜의 예상 작업 배열이다. 실제 기록은 `state.reports`만 사용한다.
- `tasks.predictedCompletionDay=null`은 이 검증 주간 내 완료 예측이 없다는 뜻이다. 영구 불가능을 뜻하지 않는다.
- `totalPlannedCost`와 `expectedIncome`은 현재 시점부터 마감까지의 추가 지출·입금이다. `projectedCash`는 예상 마감 현금, `outstandingReceivables`는 예측 마감 때 남는 **생성된 청구의 미수금**이다.
- 판정 확률·승률·법적 진실을 계산하거나 표시하지 않는다.

## 6. API·저장·실패 안전성

브라우저 `FirmEngine`와 Node CommonJS가 같은 소스를 사용한다.

```js
const state = FirmEngine.createInitialState();
const result = FirmEngine.command(state, {type: 'ACCEPT_INTAKE'});
// 성공: {ok: true, state: 새 상태}
// 실패: {ok: false, state: 원본 그대로, error: 한국어 이유}
const preview = FirmEngine.forecast(result.state);
const snapshot = FirmEngine.exportSnapshot(result.state);
const validation = FirmEngine.validateState(snapshot);
```

`ASSIGN_TASK {taskId, staffId}`, `SET_PRIORITY {taskId, priority}`, `DECLINE_INTAKE`, `ADVANCE_DAY`를 추가 지원한다. 명령은 순수 함수이며 실패 시 입력 상태가 바뀌지 않는다. RNG·현재 시각·외부 네트워크에 의존하지 않는다.

export는 wrapper 없이 JSON 친화 raw state의 독립 복사본이다. validation은 버전·달력·직무·참조·순환 의존·수행량·일별 capacity·선행 조건·완료 보고·입금 중복·청구 상태·현금/원장 합계를 검사한다. 모든 엔티티 `id`는 `^[a-z][a-z0-9_-]{0,99}$` 형식으로 제한한다. 따옴표·공백·태그 문자가 포함된 ID는 import 단계에서 거부하며, UI에서도 속성 값을 별도로 이스케이프해야 한다. `assignee: null`은 미배정 상태로 계속 허용한다. 이 JSON은 후속 Godot 화면에서 읽을 수 있는 교환 형식이며 production Godot 저장 호환을 보장한다는 뜻이 아니다.

## 7. 검증 명령과 남은 범위

### 2026-10-25 저장 무결성 보강

경제·스케줄링 기본값은 유지한다. 실제 작업이 요구량을 채운 날짜와 완료일, 고정 시나리오의 필수 업무/청구 ID 및 사건 연결, 계약과 착수금의 일치, 처리된 지급일의 입금 상태를 추가 대조한다. 저장 형식/버전은 바꾸지 않으며 정상 기존 저장과 수치 실험은 계속 지원한다.

이벤트 기록의 허용 수는 `1000 + dayIndex + 완료 업무 수 + 수임 결정 여부(0/1)`이다. 반복 사용자 변경이 기본 예산을 채우면 추가 배정·우선순위 변경을 원자적으로 거부하되, 필수 수임 결정·하루 마감·완료 기록은 별도 여유를 사용하여 주간 진행을 막지 않는다. 기존 기록을 삭제하지 않고 새 ID 충돌도 피한다. 자세한 재현은 `docs/ENGINE_AUDIT.md`를 따른다.

```sh
node --test tests/engine.test.cjs
```

## 8. 약속 책임 실험 — v0.4.0

**실험용 authored 규칙, DEC 아님.** 사용자는 2026-10-27 직전 권고의 이행과 게임적 재미 중심의 다음 실험을 승인했다. 이 절은 해당 실험을 명시적으로 선택한 상태에만 적용된다.

```js
const experiment = FirmEngine.createInitialState({
  experiment: 'commitment-v1',
  refundPercent: 50,
  openingCash: 18200000
});
const original = FirmEngine.createInitialState();
```

### 계약 결과 한 가지

- 대상은 이번에 수임하는 윤지훈의 준비 보고다. 기존 고은아 과거 업무 미수금은 소급 취소하지 않는다.
- 수임한 경우 계약 기한인 day 4의 실제 업무 수행 후 `yoon-brief`가 미완료면 착수금의 설정 비율을 환급 지출로 한 번 기록한다. 기본 실험은 50%, 즉 120만원이다.
- 기한 당일 완료하면 환급하지 않는다. 거절했으면 계약도 환급도 없다. 주간 마감 화면을 여는 행위는 정산 원인이 아니다.
- 수입과 운영비·실작업비를 처리한 뒤 환급을 반영하고, 같은 날 보고의 지출·현금에 포함한다. 별도 임의 벌점·평판·재판 결과는 생성하지 않는다.
- 원본 수임료 360만원, 착수금 240만원, 잔금 120만원, 인력 비용·시간과 무료 인계는 유지한다.
- 엔진 실험 입력은 환급 0·25·50·100%를 허용한다. 소수 원이 발생하는 별도 수치 fixture에서는 `floor(착수금 × 비율 / 100)`으로 원 미만을 버린다. UI는 이번 가설인 50%와 원본 규칙 비교만 제공한다. 50%가 최종 최적 밸런스라는 뜻은 아니다.

### 시작 조건과 목표

- 첫 주: 시작 현금 1,820만원. 빠듯한 현금: 60만원. 수임·담당·업무·기간 등 다른 기본값은 같다.
- 20만원은 별도 스트레스 검증에만 사용한다. 정상 첫날에 현금을 유지할 수 없는 조건이므로 플레이용 도전 메뉴에서는 제공하지 않는다.
- 새 주간 설정은 확인 후 초기 상태를 새로 만들 때만 적용한다. 진행 중 규칙 전환 명령은 없다.
- 목표는 약속 지키기(업무 기한 위반 0), 준비 마치기(활성 사건 준비 전부 완료), 현금 지키기(시작 및 업무일 말 현금 0 이상)다. 총점이나 자동 파산은 없다.
- 진행 중 목표는 현재 계획을 유지한 **예상**이다. 예측에 과거 실제 위반과 현금 부족도 포함한다. 주간 마감은 **실제** 결과다.

### 지표와 표현

`summarize(state)`는 상태를 바꾸지 않고 현재 현금, 생성된 확정 미수, 두 값의 합계, 시작 및 일말 최저 현금, 적자 업무일 수, 준비 완료/활성 사건 수, 완료/전체 업무 수, 과거 보고에 한 번이라도 포함된 기한 위반 업무 수, 남은 요구시간, 누적 환급액을 반환한다. 현금+미수는 법률사무소 전체 순자산이나 회계상 순이익을 뜻하지 않는다.

`forecast.summary`는 기존과 같은 일일 실행 함수로 주간 끝까지 진행한 복사본의 요약이다. 실제의 모든 과거 보고와 이후 예상 보고를 함께 반영한다. `projectedRefund`는 현재 이후 추가로 예상되는 환급액이며, `forecast.summary.refundPaid`는 예측 마감까지의 누적 환급액이다. 이미 낸 환급과 앞으로 예상되는 환급을 구분한다.

기한 위반은 나중에 일을 끝냈다고 사라지지 않는다. 완료 사건은 여전히 준비 업무 완료이며, 사건 종결·승소가 아니다. 일일 보고의 후속 업무 해제는 실제 완료 기록과 선행 조건에 근거한 표현이며 추가 생산성 보너스가 아니다.

### 저장과 검증 경계

실험 상태는 schemaVersion 1, version 0.4.0과 실험 식별자를 가진다. 원본은 version 0.3.0을 유지한다. 환급의 발생 조건·날짜·금액·원장·일일 보고를 복원 시 대조하며, 누락·중복·조건 불일치를 거부한다. 로컬 JSON 전체를 일관되게 재작성하는 행위를 막는 보안/온라인 부정행위 방지 기능은 아니다.

웹은 두 상태를 모두 이어갈 수 있다. Godot는 변경하지 않았으며 새 실험 저장 호환을 보장하지 않는다. UI의 새 규칙·저현금 조건은 시제품을 위한 게임 설계이며 현실 법률상 환불 규정이나 급여 모델을 주장하지 않는다.
