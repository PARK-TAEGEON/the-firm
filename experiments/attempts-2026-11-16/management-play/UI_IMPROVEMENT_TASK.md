# THE FIRM UI 개선 — 실행 지시문

당신은 THE FIRM의 경영 시뮬레이션 UI를 개선하는 디자이너이자 구현 담당자다. 첨부 자료를 확인하고, 디자인 제안에 그치지 말고 실제 게임에 연결된 실행본과 수정 소스, 검증까지 완성하라.

목표는 플레이어가 **현재 위험을 찾고 → 인력을 비교해 배정하고 → 변화할 결과를 이해하고 → 다음 하루를 진행**하기 쉬운 화면을 만드는 것이다. 게임의 인물·사건·문서 분위기와 시뮬레이터의 정보 비교 능력을 함께 살려라.

## 1. 입력 자료와 작업 범위를 확인하라

- 기존 `references/original/THE_FIRM_UI_Prototype_v1.html`과 `THE_FIRM_Font_Candidates.html`을 시각적 출발점으로 삼는다. 현재 녹색 경영 실행본의 외형만 확대하는 것으로 완료하지 마라.
- `project/`의 경영 v0.4 소스와 실행본은 실제 기능·상태·행동의 기준이다. 레퍼런스는 화면별 문제를 해결하기 위한 자료다.
- 기존 지침, TASK.md, RULES.md, PLAY_REPORT.md와 Git 작업 상태를 확인하고 미커밋 변경을 보존하라. 이 패키지는 독립 소스이며 원본 Git 저장소가 포함되지 않는다. 받은 환경에 저장소가 없다면 그 사실을 기록하고 실험 작업을 계속하라.
- UI·스타일·템플릿·필요한 UI 검증과 문서를 수정한다. 경제 수치나 엔진 규칙은 이번 디자인 변경에 섞지 않는다.

기존 프로토타입의 A/B/C는 **Navy & Brass / Paper & Ink / Verdict Graphite라는 시각 테마**다. 현재 v0.4의 A/B/C는 **브리핑 / 서류철 / 편성표라는 화면 구조**다. 둘을 혼동하거나 같은 선택 메뉴로 설명하지 마라.

## 2. 레퍼런스마다 역할을 제한하라

- **FM24:** 정렬 가능한 비교 목록, 선택 대상의 상세, 대응할 결정과 하루 진행의 연결.
- **Float:** 직원×날짜 편성, 가용시간·배정량·대기의 표시.
- **Suzerain:** 의뢰인 요청·계약·직원 보고의 출처와 문서 위계.
- **Carbon:** 표의 행 간격, 핵심 열, 선택 상태, 보조 정보 펼침.
- **This Is the Police 2:** 직원의 이름·초상·상태와 사건 투입의 연결.

각 자료에서 가져올 요소를 세 개 이하로 먼저 정리하라. `02_REFERENCE_BRIEF.md`와 `references/IMAGE_GALLERY.html`을 함께 확인한다. 이미지가 원격 URL이고 실제로 읽지 못했다면 확인했다고 주장하지 말고 정확한 한계를 남겨라. 여러 게임의 전체 화면을 무작정 섞지 마라.

## 3. 세 흐름을 일관된 UI로 구현하라

### 대표 업무실

오늘의 위험, 판단할 의뢰, 직원 가용시간과 다음 행동을 먼저 보여라. 불필요한 숫자 카드와 긴 설명문을 반복하지 않는다. 사건이나 업무를 눌렀을 때 관련 상세·조정으로 연결한다. 하루 진행은 현재 판단 상태와 연결된 눈에 띄는 행동이어야 한다.

### 사건 상세·수임 검토

의뢰인 요청, 계약 조건, 준비 업무, 담당·기한, 현금·확정 미수와 선택의 영향을 구별하라. 사건 목록과 선택한 사건의 문맥을 유지하며 상세를 읽게 한다. 준비 완료를 사건 종결이나 승소로 표현하지 않는다. 계약 미이행 환급 실험은 수임 전에 조건을 보여라.

### 인력 편성

직원별 시간, 선행 업무 대기, 담당 변경, 변경 전후의 완료·지연·비용 차이를 비교할 수 있게 하라. 담당 책임, 오늘 실제 처리량, 남은 전체 업무량을 혼동하지 마라. 직원이 법률 업무에 배정될 수 없는 경우에는 이유를 표시한다. 과다 배정은 허용되지만 실제 수행은 가용시간 안에서만 일어난다는 규칙을 정확히 드러내라.

현재 데이터인 기존 사건2건·신규 의뢰1건·직원4명·최대7업무·5업무일을 같은 값으로 사용한다. 매일 보는 핵심 정보와 필요할 때 여는 상세를 구분한다.

별도 선호 지시가 없으면 **Verdict Graphite를 운영 화면의 기본 방향, Paper & Ink를 문서 영역의 표현**으로 삼아 한 개의 완성도 있는 주력 시안을 먼저 구현하라. 이는 기존 테마와 폰트 비교 기능을 삭제하거나 최종 선택을 확정하라는 뜻이 아니다. 기존 후보를 확인할 수 있는 기능을 유지·복원하고 실제 로딩 여부를 표시하라.

## 4. 가독성을 실제 크기로 검수하라

한국어 본문14~16px, 보조 문구12~13px, 중요한 조작 약16px, 표 행48~56px를 초기 가설로 사용한다. 이 값 자체를 통과 기준으로 삼지 말고 실제 읽기와 조작을 확인하라.

- 핵심 데이터를10~11px로 축소해 넣지 않는다. 보조 정보는 접거나 상세로 옮긴다.
- 업무명·담당·남은 시간·기한·예상 완료·조정 행동을 같은 시야에서 비교한다.
- 선택·대기·미배정·지연·완료를 색 외의 이름과 표시로도 구분한다.
- 금액·날짜·시간의 정렬, 단위와 양수/음수 표현을 일관되게 한다.
- 1366×768과1440×900에서 중요한 정보와 행동이 잘리지 않는지 확인한다.
- 390px에서도 주요 행동과 모달 적용 버튼에 접근할 수 있어야 한다. 표 내부 스크롤은 허용하되 페이지 전체가 가로로 밀리지 않게 한다.
- 글꼴은 후보 이름뿐 아니라 실제 로딩, 굵기, 숫자, 한국어 줄바꿈과 대체 글꼴 상태도 확인한다. 온라인 후보를 오프라인에서도 로드한 것처럼 주장하지 않는다.

## 5. 경영 규칙과 저장의 의미를 보존하라

UI는 실제 FirmEngine의 상태·명령·예측을 사용한다. 화면에 맞춘 별도 경제 모형이나 가짜 진행 상태를 만들지 않는다. 다음은 수정 금지 경계다.

- 원본0.3 저장은 원본 규칙,0.4 실험 저장은 해당 계약 규칙으로 이어간다. UI 버전 표시를 바꾸어도 engine state.version/schemaVersion을 함께 올리지 않는다.
- 계약 미이행 환급, 날짜 진행 횟수, 보수·업무비·운영비·가용시간·무료 인계와 실제 수행 기록을 유지한다.
- 현금과 확정 미수, 예상과 실제, 준비 완료와 기한 준수를 구별한다. 최저 현금은 시작 및 각 업무일 말 잔액의 최솟값이다.
- 조회·테마 변경·글꼴 변경·미적용 배정 초안·취소가 게임 상태를 바꾸면 안 된다. 화면 설정은 게임 저장과 구분한다.
- 새 능력·평판·채용·대출·파산·재판·장기 캠페인·Godot 시스템을 추가하지 않는다.

## 6. 구현과 검증을 끝내 전달하라

일상적인 디자인·구현 선택은 근거를 남기며 진행하고 매 단계 승인을 기다리지 마라. 중요한 입력이 없거나 지침이 충돌하면 확보한 범위의 작업을 계속하고 정확한 부족 항목을 보고하라. 읽지 못한 이미지를 본 것처럼 설명하지 마라.

기존 회귀와 변경한 UI 흐름을 실행하라. 테스트 DOM 선택자를 바꾸어야 한다면 실제 게임 결과의 기대값을 편의상 바꾸지 마라. 가벼운 스타일 변경 자체를 고정 수치 검사로 과도하게 테스트하지 말고 실제 화면의 읽기·넘침·조작과 상태 보존을 확인한다.

프로젝트에서 `python tools/build.py`, `node tools/play-verify.cjs`를 실행한다. Playwright와 Chromium이 준비되면 `node tools/play-verify.cjs --browser`도 실행한다. 환경에 없는 도구나 사람 플레이를 실행했다고 기록하지 않는다.

최종 결과에는 실행 HTML, 수정 소스, 주요 화면의 전후 비교, 실제 검증 명령·결과, 기존 프로토타입에서 계승한 요소와 남은 한계를 포함한다. project/REPORT.md와 REVIEW_PACKET.md를 현재 결과로 갱신하라. 임시 이미지는 정리하고 필요한 글꼴 라이선스와 이미지 출처를 보존하라. Git push나 외부 배포는 하지 않는다.

기능 검증·가독성 검수·사람의 재미 판단을 구분하라. 최종 보고는 **바뀐 플레이 경험 → 화면 변경 → 실제 검증 → 남은 판단** 순서로 작성한다.
