## Submission Rules

- SubmissionAttempt is an explicit atomic action, not an inferred status.
- It preserves stable identity and the accepted closure's required refs for document/version, submitter, team, matter, stage, target, route, package, time/event order and deadline context.
- Creating an attempt does not itself mean filed, received, accepted or included in CourtRecord.
- The procedural result is separately materialized and immutable.
- Clear authored results are deterministic. Any accepted bounded variation is materialized once and cannot reroll on read, redraw or reload.
- Merits, Argument choice, lawyer capability, partner approval or client approval cannot bypass supplied procedural requirements.
- Weak merits cannot be used as a hidden procedural rejection reason.
- Future/unmaterialized results are not exposed to player UI or read APIs.
- Invalid or duplicate IDs, mismatched document ID/version, wrong actor/team/matter/stage, unauthorized target/route, unknown or foreign-matter package members, unsatisfied dependencies and invalid event order are rejected before mutation.
- Same-lineage finalized revisions must reuse the already-allocated `document_id` with a new unique `document_version`; the store and APIs must address versions by the composite pair and retain every earlier pair. A distinct `document_id` starts a separate lineage and is not a revision.
- Creating a later real version requires a distinct completed DraftWorkProduct ID/version pair with matching matter/stage/team/document type. It does not define generic edit, amendment, supersession or cure behavior.
- Earlier real versions remain submission-eligible after a later version exists. Only an unknown `document_id` or a version absent from that known lineage is an invalid/stale finalized-document reference.
- Omission of a known authored required package member is not command invalidity: it preserves the valid attempt and later materializes `rejected_defective` with `missing_required_package_member` through the separate result command.
- Rejected commands leave the complete authoritative state and journal unchanged.

## CourtRecord Rules

- CourtRecordEntry is created only through an explicit materialization command/event.
- Materialization requires the exact procedurally eligible artifact and explicit inclusion rule accepted for VS-005.
- Draft, FinalizedDocument or SubmissionAttempt alone cannot enter CourtRecord.
- A procedurally accepted artifact cannot enter CourtRecord when the explicit inclusion/materialization gate is absent or unsatisfied.
- CourtRecordEntry preserves the source artifact/version, attempt, procedural result, materialization rule/event, matter/stage, actor/team where applicable, content version and event order.
- CourtRecord history is append-only. Current projection may derive from immutable events but cannot delete or rewrite prior attempts, results or entries.
- CourtRecord materialization does not create or mutate JII, ChoicePoint, CourtFactFinding, judge interpretation, adjudication state, Judgment or appeal state.
- UI wording must not imply that filed/accepted/recorded content was considered, believed or adopted by a judge.
