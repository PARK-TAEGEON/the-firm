## Implement

Add minimum playable Investigation flow.

The player must be able to:

1. inspect an investigation opportunity / known gap
2. create or assign an investigation task
3. execute explicit investigation work
4. receive deterministic authored outcome:
   - success
   - partial success
   - failure
5. acquire new SourceMaterial only through an explicit acquisition event
6. inspect newly acquired authorized source scope through the existing CaseFile path

Investigation must reuse the existing:

TaskDefinition
→ Assignment
→ Execution
→ Completion

semantics where appropriate.

Generic Task / Assignment / Execution / Completion lifecycle remains owned by the existing WorkService semantics.

Investigation-specific behavior, including InvestigationResult and AcquisitionEvent production, may be implemented in a dedicated investigation-specific service when separation is justified by the existing code structure.

VS-003 must not redesign the generic WorkService lifecycle merely to support Investigation.

Any investigation-specific service must consume the existing Task / Assignment / Execution / Completion lifecycle rather than creating a parallel task system.

## Semantic Boundaries

InvestigationResult
≠ SourceMaterial
≠ SourceAssertion
≠ ReviewWorkProduct
≠ CaseTheory
≠ CourtRecord
≠ CourtFactFinding

Investigation may reveal or acquire sources.

Investigation must NOT directly mutate:

- existing SourceAssertion
- CaseTheory
- CourtRecord
- CourtFactFinding
- Judgment

Newly acquired material enters CaseFile only through explicit acquisition provenance.
