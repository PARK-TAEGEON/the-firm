# VS-004 Task Contract (Revised)

## Task

VS-004 — Legal Research, Issue Analysis, and Argument Construction

## Problem

The current playable vertical slice reaches Investigation and can acquire provenance-bearing `SourceMaterial`, but it has no playable canonical flow from Legal Research through `RecordedLegalExtraction`, `RuleStatement`, `InterpretationCandidate`, `IssueAnalysis`, and `Argument`.

VS-004 solves only that missing playable flow. It must connect the existing VS-003 baseline to authored legal research, explicit work, recorded extraction, analysis, argument construction, and argument selection without inventing later-stage litigation semantics or a canonical `Strategy` object.

## Prerequisites

VS-004 implementation must NOT begin until all of the following are true:

1. VS-003 has received an explicit Reviewer verdict of `PASS`.
2. That PASS is recorded in the VS-003 review history under `.agent/reviews/VS-003.md`.
3. Any design document required for implementation is formally in an accepted/promoted state.
4. If a required DEC/TEST is still Proposed, implementation must stop and report the exact unresolved dependency.

A TEST recommendation to promote a DEC does not itself change the DEC status.

Do not silently treat Proposed design as Accepted.

## Goal

Completed VS-003 runtime 위에 최소한의 Legal Research와 Issue Analysis gameplay를 구현한다.

플레이어는 현재 selected Issue, current CaseTheory, ReviewWorkProduct, Investigation 결과와 newly acquired SourceMaterial을 바탕으로:

current CaseTheory
+ selected Argument(s)
+ current IssueAnalysis

를 보여주는 non-canonical presentation view여야 한다.

## Legal Research Rules

LegalSource existence does not mean the player has discovered it.

Discovery does not mean review.

Review does not mean correct understanding.

Correctly authored RuleStatement extraction must preserve provenance to:

- LegalSource ID
- source version
- exact reviewed scope
- research task/work provenance
- actor/team/matter/stage
- content version

An InterpretationCandidate must remain an analysis candidate, not hidden truth.

IssueAnalysis must preserve, where applicable:

- Issue reference
- completed research basis
- reviewed LegalSource references
- RuleStatement references
- InterpretationCandidate references
- source/content versions
- actor/team/matter/stage provenance

No hidden correct-law oracle may be exposed to gameplay or UI.

Do not introduce:

- winning authority
- best precedent score
- universal legal strength score
- automatic correct interpretation flag

---

## Argument Rules

Argument is an internal litigation analysis/construction object.

An Argument must preserve provenance to:

- active Issue
- current CaseTheory version
- IssueAnalysis
- supporting RuleStatement(s)
- relevant LegalSource(s)
- relevant ReviewWorkProduct(s)
- relevant InvestigationResult / acquired SourceMaterial references where applicable
- known gaps / assumptions / challenges where applicable
- actor/team/matter/stage
- content version

Argument construction must NOT:

- mutate SourceAssertion
- mutate CourtFactFinding
- create Submission
- create CourtRecord
- create adjudication result
- create Judgment

Different authored Argument choices must remain meaningfully distinct in provenance and references.

## Acceptance Criteria

VS-004 passes only if every criterion below is satisfied. Any unmet criterion is a failure.

### Governance and scope

- VS-003 has an explicit recorded Reviewer `PASS`, and every required DEC/TEST dependency is formally accepted or promoted before implementation begins.
- Implementation changes are confined to `Allowed Changes`; no forbidden or next-stage work is started.
- No canonical `Strategy` object, identity, version, lineage, lifecycle, status machine, or persistence semantics exists.
- No `Submission`, filing result, `CourtRecord`, `CourtFactFinding`, adjudication, `Judgment`, appeal/remand, save/load, or other VS-005-or-later behavior is implemented or materialized.

### Domain and workflow semantics

- `LegalSource`, `RecordedLegalExtraction`, `RuleStatement`, `InterpretationCandidate`, `IssueAnalysis`, and `Argument` remain distinct canonical concepts and records.
- Discovery is not review; review is not extraction; extraction is not synthesis; synthesis is not interpretation; interpretation is not issue analysis; issue analysis is not argument construction or selection.
- Opening or discovering a `LegalSource` does not automatically complete research or create a `RecordedLegalExtraction`, `RuleStatement`, `InterpretationCandidate`, `IssueAnalysis`, or `Argument`.
- Legal Research uses the existing generic `TaskDefinition → Assignment → Execution → Completion` lifecycle through `WorkService`; `LegalResearchService` is limited to research-specific prerequisites and materialization.
- Argument creation and Argument selection are separate atomic service operations.
- Every selection appends an immutable `ArgumentSelectionEvent`; prior selection events cannot be mutated, replaced, or deleted.
- Authored content provides at least two meaningful alternative Argument paths whose observable provenance and references differ; neither is encoded as hidden truth or an automatic winner.
- The playable UI supports the required Legal Research, analysis, Argument creation/selection, and derived current-approach inspection through service APIs only.

### State, API, and determinism

- All authoritative mutation and validation occurs in services, with `SliceService` remaining the façade/API boundary.
- Rejected commands leave the complete authoritative state and event journal unchanged.
- Every returned projection is a nested deep copy; caller mutation cannot change authoritative state.
- Repeated reads create no events, persistent IDs are not reused, and the same authored content plus command sequence deterministically reproduces state and event ordering.
- Required identities, versions, exact scopes, work provenance, actor/team/matter/stage provenance, content version, and event order are preserved as specified by `Required Provenance` and the detailed workflow rules in this contract.

### Regression and handoff gate

- All legacy, VS-001, VS-002, VS-003, and VS-004 regression suites pass with zero failures and exit code `0`.
- The VS-004 regression runner returns nonzero on any failure and covers every case under `Required Regression Cases`, including positive and negative invariants and rejected-command atomicity.
- The main-scene headless smoke run exits `0` with no script or scene-load error.
- `litigation-skeleton/REVIEW_PACKET.md` is updated with the exact implementation result, changed files, implemented user actions, UI verification actually performed, public APIs, state references and record shapes, canonical object boundaries, immutable event details, authored legal content and alternative Argument paths, test commands/check counts/failure counts/exit codes, fixture/injected portions, unimplemented/TBD items, untouched design decisions, scope audit, and VS-005 handoff.
- The original `Done Condition`, `Required Regression Cases`, `Validation`, and `Completion Handoff` requirements remain cumulative and must all pass.
