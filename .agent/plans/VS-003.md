# VS-003 Implementation Plan

## 1. Current Runtime Assessment

The existing VS-001/VS-002 runtime is sufficient to represent VS-003 additively.

Reusable runtime objects:

- `SliceState`
  - Owns authoritative actors, teams, sources, acquisitions, Task definitions/instances, assignments, executions, completions, WorkProducts, Issues, CaseTheory versions, time allocations, and journal history.
  - `snapshot()` already returns a recursive copy for regression inspection.
- `SliceService`
  - Existing public façade and content-validation boundary.
  - Owns session initialization and Case File queries.
  - `case_file_projection()` already derives visibility exclusively from acquisition records.
  - `read_source()` already enforces exact source/version/scope authorization.
- `WorkService`
  - Owns Task assignment, explicit execution, dependency checks, time allocation, completion, and journal mutation.
  - Already distinguishes TaskDefinition, TaskInstance, Assignment, Execution, Completion, and WorkProduct.
- Existing VS-002 dependency objects:
  - completed review Task
  - `ReviewWorkProduct`
  - selected Issue
  - current versioned `CaseTheory`
  - `VS-GAP-001`
- `SlicePresenter`
  - Converts service projections into UI-only text and list rows.
- Existing UI
  - Sends explicit commands through `SliceService`.
  - Does not directly mutate `SliceState`.

Relevant limitations in the current implementation:

- `WorkService.execute_task()` and `complete_review_task()` are Evidence Review-specific despite the otherwise generic Task state model.
- Content validation currently rejects every TaskDefinition whose family is not `evidence_review`.
- Investigation outcomes and acquisition events have no runtime collections or APIs.
- All authored SourceMaterial definitions are loaded into the internal source catalog, but Case File projection and reads hide them until an acquisition authorizes exact scopes. This existing separation is reusable.
- Adding authored Task instances at session start would alter VS-001’s fixed seven-event initial history. Investigation Task instances should therefore be created explicitly at runtime.

Repository document status note:

- The checked-in `DEC-LITIGATION-021`/`TEST-020` headers identify v0.1 as Proposed, although later documents refer to v0.2 Accepted.
- This plan does not adopt their TBD algorithms, taxonomies, probability rules, legal powers, or hidden-world mechanics.
- The binding VS-003 Task Contract itself fixes the slice-specific requirements needed here: explicit Task lifecycle, authored deterministic success/partial/failure, explicit acquisition provenance, and exact-scope visibility. Those requirements can be implemented without resolving the remaining proposed/TBD semantics.

## 2. Proposed Runtime Flow

```text
Visible KnownGap / authored public investigation opportunity
→ create_investigation_task()
→ WorkService creates Investigation TaskInstance
→ assign_task() using the existing API
→ execute_investigation_task()
→ WorkService validates assignment, dependency, actor/team, work, and time slot
→ explicit Investigation Execution is recorded
→ complete_investigation_task()
→ authored outcome is selected by the already-bound action identity
→ WorkService records generic Completion
→ InvestigationService creates immutable InvestigationResult
→ InvestigationService appends AcquisitionEvent for success/partial success
→ existing Case File authorization derives newly visible exact scopes
→ case_file_projection()/read_source() expose only acquired scopes
```

Task creation should be allowed from the already-visible known gap, even before its review dependency is finished. Assignment may also occur while blocked. Execution must fail with `incomplete_dependency` until the review Task is completed.

After the generic Task dependency is complete, investigation execution must additionally require:

- a completed ReviewWorkProduct from the dependency Task;
- the required Issue to have been selected;
- a current CaseTheory version for the same matter/team;
- the current theory to retain the investigation opportunity’s KnownGap starting basis.

The authored slice should provide three independent opportunities so all outcomes are playable without randomness:

- Success: acquires every authored scope for one new source.
- Partial success: acquires only the authored subset of another source; its remaining scope stays inaccessible.
- Failure: records a bounded failure result and no acquisition.

The outcome definition remains private to the service. Opportunity projections expose only known basis, purpose, bounded domain, and action description—not outcome status, target source identity, hidden scope identity, or source contents.

## 3. Service Ownership

Choose **B: introduce a narrow Investigation-specific service while keeping the generic Task lifecycle in WorkService**.

This follows the current code structure:

- `SliceService` remains the public façade and validation/composition boundary.
- `WorkService` remains the sole owner of TaskInstance, Assignment, Execution, Completion, time-allocation, and Task-state mutations.
- New `InvestigationService` owns only:
  - investigation prerequisite validation beyond generic Task dependencies;
  - authored action/result resolution;
  - `InvestigationResult`;
  - `AcquisitionEvent`;
  - investigation projections.

`WorkService` requires narrow additive entry points for Investigation Task creation, execution, and completion because its existing execution/completion methods encode Evidence Review fields. The existing methods must not be generalized into a payload DSL or rewritten.

The completion command must use a complete preflight before its first mutation:

1. Validate actor/team, task family/state/assignment, performed work, dependencies, action binding, current Issue/Theory basis, result identity, acquisition identity, authored source/version/scopes, and route.
2. After preflight succeeds, perform only non-failing deterministic writes.
3. Let `WorkService` record Completion.
4. Record `InvestigationResult`.
5. Append `AcquisitionEvent` when applicable.

This keeps invalid commands atomic while preserving service ownership.

## 6. State and Provenance Plan

### InvestigationResult

Each result is a distinct immutable runtime object containing at least:

- result ID;
- authored outcome: `success`, `partial_success`, or `failure`;
- Task ID and TaskDefinition ID/version;
- Assignment ID;
- Execution references;
- investigation action ID;
- starting basis references;
- bounded search domain;
- actor and team;
- matter and stage;
- authored result summary;
- acquisition references, if any;
- limitations/remaining scope description;
- content version;
- result event order.

It does not contain or create SourceAssertions, ReviewWorkProducts, CaseTheory versions, CourtRecord entries, findings, or judgments.

### AcquisitionEvent

Every VS-003 acquisition must append a new immutable acquisition entry with:

- `id`
- `source_id`
- `source_version`
- `scopes` as the exact authorized scope IDs
- `actor_id`
- `team_id`
- `matter_id`
- `stage_id`
- `investigation_action_id`
- `investigation_task_id`
- `investigation_result_id`
- `route`
- `provider_ref`
- `event_order`
- `content_version`

The source definition itself remains immutable authored content. The AcquisitionEvent changes firm-side authorization and therefore causes the existing Case File projection to materialize the acquired SourceMaterial/scopes.

### Event ordering

For a fixed command sequence:

```text
task_created
→ task_assigned
→ task_executed
→ task_completed
→ investigation_resolved
→ source_acquired (success/partial only)
```

Each journal event receives the next monotonic order. Replaying identical content and commands must reproduce the same state and event order.

### Exact-scope visibility

- `case_file_projection()` continues to include a source only when the viewer team has an acquisition for its exact source version.
- It includes only scope IDs named by acquisitions.
- `read_source()` continues to reject any requested scope outside that union.
- Partial success therefore reveals only its acquired subset.
- Other scopes of the same source, other unacquired sources, their titles, identities, and contents remain hidden.
- Investigation projections must not serialize private authored outcome data before resolution.

### Identity rejection

- Content validation rejects duplicate investigation action IDs globally.
- Runtime Task creation rejects reused Task or creation-event identities.
- Completion rejects a reused InvestigationResult identity before mutation.
- Success/partial completion rejects any reused acquisition identity, including collision with initial acquisition IDs.
- Identity checks span all persistent runtime objects and journal events.

### Failure semantics

Two different cases must remain explicit:

- An authored `failure` is a valid InvestigationResult. It completes the Task and preserves the failed attempt/result history, but creates no AcquisitionEvent and changes no source authorization.
- A rejected command—invalid actor/team, dependency, duplicate identity, state, allocation, or provenance—must leave the entire authoritative snapshot and journal unchanged.

## 8. Regression Plan

Structure `run_vs003_regressions.gd` with reusable helpers:

- load/start content;
- bootstrap the VS-002 chain through review completion, Issue selection, and current CaseTheory creation;
- create/assign/execute an Investigation Task;
- assert rejected command plus full-snapshot equality;
- replay a fixed command sequence.

Required cases:

- **Valid investigation success**
  - Complete dependencies and success action.
  - Verify separate Task, Execution, Completion, InvestigationResult, and AcquisitionEvent.
- **Partial investigation result**
  - Verify `partial_success`, exact acquired subset, and recorded limitation/remaining scope.
- **Failed investigation**
  - Verify valid failure result/history, no acquisition, and no new visible source.
- **Invalid actor/team**
  - Exercise create, execute, and complete authorization gates as appropriate.
  - Verify full state equality after rejection.
- **Before dependency completion**
  - Create and assign the Task before the review dependency finishes.
  - Verify execution rejects with `incomplete_dependency` and no mutation.
- **Duplicate investigation identity**
  - Reject duplicate Task/creation-event and reused InvestigationResult identities.
- **Duplicate acquisition identity**
  - Reject collision with an initial or previous acquisition ID before any completion-side mutation.
- **Unauthorized scope remains inaccessible**
  - Query hidden source/scope before acquisition.
  - Ensure opportunity projection does not reveal private outcome identifiers.
- **Acquired exact scope becomes visible**
  - Verify Case File row, acquisition history, and successful exact-scope read.
- **Unacquired scopes remain hidden**
  - For partial success, verify projection exclusion and `scope_not_acquired`.
- **Failed action leaves authoritative state unchanged**
  - Snapshot around every rejected invalid/duplicate/dependency command.
- **Returned projections are deep copies**
  - Mutate nested Investigation projection, result, acquisition, and Case File values; re-query and compare.
- **Repeated query creates no event**
  - Repeat Investigation, Case File, and source queries; journal and snapshot stay identical.
- **Deterministic sequence**
  - Run the same bootstrap and all three authored outcomes twice with identical IDs/order; compare full snapshots and journal order.
- **No adjudicative objects**
  - Assert no CourtRecord, CourtFactFinding/finding, or Judgment key/object/event.
- **Boundary preservation**
  - Snapshot existing SourceAssertions and CaseTheory before investigation and verify byte-for-byte equality afterward.
  - Verify no ReviewWorkProduct is created by acquisition.

## 9. Risks and Boundary Checks

- **WorkService redesign risk:** Do not replace current methods with a generic payload/handler framework. Add only the three narrow lifecycle operations required by Investigation.
- **Lifecycle duplication risk:** InvestigationService must never assign, execute, complete, allocate time, or set Task state directly.
- **Hidden-state leakage:** Private authored outcome/source references must not appear in opportunity or TaskDefinition projections.
- **Acquisition bypass:** Never add a source directly to a Case File-visible collection. Visibility must derive from AcquisitionEvent scope.
- **Scope widening:** Do not treat acquiring one scope as acquiring the entire source or another version.
- **Epistemic laundering:** Do not generate SourceAssertions, analyses, Issue conclusions, or CaseTheory revisions from acquired contents.
- **Failure ambiguity:** Preserve authored failure history while keeping rejected commands atomic.
- **Provenance loss:** Never overwrite prior results or acquisitions; append new identities and event order.
- **Content-version compatibility:** Update the single VS-001 content-version expectation while preserving its seven-event initial baseline.
- **Task projection coupling:** Existing presenter code assumes the first Task is the Review Task. Investigation Tasks should be created after session start and investigation UI should select tasks by ID/family, never array position.
- **TBD expansion:** Do not add Leads, retries, provider AI, search algorithms, probability, investigator stats, costs, legal authority, or universal status taxonomies. The three outcome labels are the Task Contract’s fixture-local authored vocabulary.
- **VS-004 boundary:** Newly acquired material remains unreviewed. No Legal Research or automatic CaseTheory revision begins.

## 11. Planner Verdict

The current runtime can satisfy VS-003 through additive state, validation, façade APIs, narrow WorkService lifecycle extensions, and a dedicated InvestigationService. Existing acquisition-derived Case File authorization already provides the critical exact-scope boundary, so no accepted semantic architecture, VS-001/VS-002 API, hidden-truth rule, or future-stage system must be changed.
